# X3AP scene-node leak triggered by Mayhem 3 / ZMap backgrounds (2026-09-29)

Summary for the Mayhem 3 / ZMap maintainers. Measured on X3: Albion Prelude 3.4 (X3AP.exe,
SHA-256 fdbf3418…) with Mayhem 3 and a galaxy generated by ZMap with the Fog slider above 0.

## Symptom

In most Mayhem sectors the frame rate falls steadily the longer the player stays (56 fps to
33 fps over about 5,000 frames in our run), and save files made after a long stay grow. A
sector change or reload restores the frame rate.

## Cause (engine bug, exposed by the data)

Every frame the engine's dust-scene fill (function 0x0041efc0, the worker behind
`INS_UpdateDustScene`) tops the sector's dust up to the background's `NumDustInstances`
(TBackgrounds column 19). For each missing instance it allocates a scene node **first** and
loads the dust body **afterwards** (column 11-18 rates pick one of `nebula_<family>_dust_part01..08`).
When the body does not exist, the code skips the attach and drops the node pointer
(branches at 0x0041f3d1 / 0x0041f436 / 0x0041f447 to 0x0041f4d1). The node stays on the
render manager's unattached list forever, and because it was never attached to the dust
scene, the next frame allocates the same number again. The per-frame animation tick
(0x0048f550) walks that list, so frame time grows linearly with the leaked count
(about 77 ns per node per frame on our machine). Only the render-manager clear on sector
change / load / quit frees the nodes.

Leak rate per frame = `NumDustInstances` of the sector's background, whenever that family
has no dust bodies.

## Why Mayhem hits it

ZMap's `CreateBackgrounds` (Persist.cs) rewrites every row of `template_TBackgrounds.txt`
when the Fog slider is above 0: columns 11-18 (dust body rates) become 1 and column 19
("fog density", which the engine reads as `NumDustInstances`) becomes a random value in the
slider's band. But only 134 of the 317 nebula families in the Mayhem cats ship
`nebula_<family>_dust_partNN` bodies. In the generated `addon/types/TBackgrounds.txt`
(248 rows) 170 rows request dust from a family that has none; e.g. row 103 `litcube75`
asks for 27 instances and leaks 27 nodes per frame. Stock X3AP has one such row
(`xtmgreenring`), which is why the stock game is barely affected.

Script: `dust_bodies.py` in this folder lists every row and the missing parts
(`PYTHONPATH=tools/analysis python3 dust_bodies.py <game root>`).

## Fixes on the data side

Either of these removes the leak without any engine change:

1. In ZMap, set columns 11-18 and 19 to 0 for families that have no
   `nebula_<family>_dust_part01..08` files (check the cats at generation time, or keep a
   list of the 134 families that have them).
2. Or ship dust bodies for the 170 families (any of the four body formats works).

Those sectors currently show no dust anyway, so option 1 changes nothing visible.

## Fix on our side

x3-mod (the D3D9 proxy) patches the failure path so the node is released and the fill stops
for that frame (`dust_leak_fix`, default on). That protects players regardless of the data,
but the data fix is the right one for everyone else.
