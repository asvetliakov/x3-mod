## Analysis protocol

Copy the selected session log and its readbacks/dumps from the installed
capture directory into a new `/tmp/x3-bottleX3-run<N>/` directory before
analysis. Inspect filenames, timestamps and file sizes first; do not overwrite
an earlier snapshot. Copy only files belonging to that run, and distinguish
complete sessions from a still-running session. The capture directory is
reported by `tools/manage.py status` and the session's `capture_dir=` field.

Use bounded streaming analysis under `tools/analysis/` rather than reading a
large log whole. Record build provenance, flags, scene/save differences,
acceptance counters and phase timings in the verification document and update
`docs/status.md`. Keep raw logs, mesh dumps, textures and readbacks local and
untracked. Compare run 5 with the preserved `/tmp/x3-bottleX3-run16/` fixed-EV
baseline; if the scene differs, distinguish that from an exposure regression.
Run 16 had `taa_debug=0`, sharpen 0 and mip bias 0. Its snapshot initially
contained only the 59 MB log; a bounded scan identified seven successful
`hdr_` readbacks, recovered from the live capture directory by matching names,
sizes and modification times within the session. Their recovery hashes and
source metadata are saved locally in `recovered-hdr-inputs.json`. There are
no `taa_` or `present_` records, so those unresolved HDR inputs are not a
measured resolved/presented-image baseline.

For a scoped modeled comparison, use the **new** capture's
`taa_<device>_<frame>.rgba16f` and the validated AgX reference with exposure
multiplier 1.0 and matching decode/look/clamp settings. Pair it with a successful
same-device/frame `present_` readback without fallback/unwind. This models fixed
EV 0 write-back of the same resolved frame, before later game glow/HUD rendering;
it does not reconstruct a different temporal history or the old run's screen
image. `hdr_` is the unresolved scene input and is not the paired write-back
input. No extra launch is needed solely for this modeled comparison.

Separate diagnostic overhead and fixture microbenchmarks from game frame time
and uninstrumented load time. Verify-mode work is intentionally duplicated, so
its total load time does not predict fast-mode performance.
