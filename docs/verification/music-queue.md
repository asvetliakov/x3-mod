## Open

- Unflown. The first flight's expectations are in the architecture note ("What the first flight must show"): the KC
  row `applied` with the vanilla bytes, a defer / park / release on one gate jump with the old track audible through the
  warp, a collapse on a second jump, the vanilla fallback on a combat start and on a save, a same-id loop with no queue
  row, and no `refuse reason=cells` on a `0x0db54` stop with the alert at 0/0.
- The frame-cell values are read for the first time in that flight (Run 189 logged depths only); a `cells` refusal row
  carries all six for a correction of the indices.
- Whether the loader's peephole pass (`0x0049e4f0`) leaves the `op6f; jt` window as the file has it is bound by the exact
  in-memory byte compare: a rewritten window refuses with the bytes seen and gate jumps keep the vanilla fade.
- Docking is settled by `music_dock_keep` (2026-10-25, unflown): a docking request keeps the playing track. The MD's
  `DoPlayMusic` stays deferrable like a sector change.
- Save keep and docking keep are unflown; their flight expectations are items 5 and 6a of the architecture note. Open
  there: whether the DirectSound status query keeps reporting the end of a buffer the pump stopped during the save (a
  return-2 save, now handled by clearing O's flag 2) and the attribution of the 1.5.1 flight's 3 synchronous ends to
  the pause (the row now names the caller). A pause while an ordinary sector change is pending still ends the queue
  (the new track from 0 after the unpause); keeping it would need the proxy to resume O itself at the unpause (a Run of
  O and flag 2 restored from Present), a new engine call context that was not built.
- Audible continuity of the orphan across its re-key and the gap at the release (about one frame plus the DirectSound
  prebuffer the vanilla same-id replay also has) are settled only by the flight.
