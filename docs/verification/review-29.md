## Checklist

1. **One hook table, three branches** (`src/proxy/loading_trace.h:24-40`,
   `loading_trace.cpp:454-506`). The `Operation` enum is the concatenation
   of the 23 original import rows (`FileOpen` … `GzWrite`), the 20 probe
   batch 2 rows (`InflateInit` … `HandleClose`) and the three mesh method
   rows; `hooks[]` has 43 entries and `static_assert(import_count ==
   Operation::MeshPointReps)` (`loading_trace.cpp:504`) pins the table to the
   enum, `probe_row_begin/end` (`loading_trace.h:41-42`) bracket exactly the
   20 probe rows. The 26 `light::` rows carry `static_assert(is_same_v<…>)`
   signature checks against the Win32 prototypes (`loading_trace.cpp:507-526`);
   the adjacency dump helper, the cache/adjacency services and the gz routing
   (`gz_buffer_active`, `loading_trace.cpp:453`) coexist in the same unit
   without touching each other's rows.
2. **Gates and what a plain run patches.** `install()`
   (`loading_trace.cpp:862-958`) returns before reading the import
   directory unless `X3M_TELEMETRY=1` or `X3M_GZ_BUFFER=1` (`:866`); the
   gz-only path patches the six gz rows and nulls every other slot
   (`:928-937`); the telemetry path nulls the probe rows unless
   `X3M_LOADING_PROBES=1` (`:951`) and calls `loading_probes::initialize()`
   only then (`:957`). `X3M_MESH_ADJACENCY` / `X3M_MESH_ADJACENCY_DUMP` are
   read on the telemetry path only (`:941-946`); `X3M_RESOURCE_READ` /
   `X3M_DAT_HANDLES` are read by `resource_reader::initialize()`
   (`resource_reader.cpp:100-110`), which returns `disabled` before any
   byte check or claim when both are off. A plain `--direct` run therefore
   patches nothing: `loading_trace::initialize` is not called
   (`capture.cpp:1395`), the resource reader is `disabled`, the profiler needs
   `X3M_PROFILE`, `object_trace` (`object_trace.cpp:162`),
   `object_lifetime` (`object_lifetime.cpp:413`) and the scene hook
   (`scene_hook.cpp:90-96`, off without `X3M_MOTION_OUTPUT=1`) stay disabled;
   the only behavioural difference from the review-26 build is the
   `frame_end … elapsed_ms dt_ms qpc` line (`capture.cpp:514-525`).
3. **Install order vs the trampoline window.** `load_backend`
   (`loader.cpp:19-63`) runs `initialize_log` first, which does the only
   `engine_patch` claims in the process (`loading_trace::initialize` →
   `loading_probes::initialize`, then `resource_reader::initialize`, which
   chains behind the probe's `resource_read` site when it exists,
   `resource_reader.cpp:119-122`), before the backend loads and before
   `object_trace`, `object_lifetime` and `scene_hook` install. The window
   closes at the first `Present` (`capture.cpp:510-513`), after which every
   `engine_patch::claim`/`claim_call` reports `late_claim`
   (`engine_patch.cpp:92,148`). The scene hook, object trace and lifetime
   patches use their own `VirtualProtect` paths, not `engine_patch`, so the
   scene hook's reinstall on a device created after the last one was
   destroyed (`capture.cpp:1235-1238`) is unaffected by the closed window.
   Site addresses do not overlap: scene hook `0x004721b1`, probe sites
   `0x004bc680 … 0x00527869`, resource reader on the probe's `0x004e8880`
   (`resource_reader.cpp:16`), pool `E8` sites `0x004e87ff`/`0x004e9392`
   (`resource_reader.cpp:31`) inside the reader's callers, none of them the
   scene-hook or probe bytes. The present
   readbacks (`motion_output.cpp:756`, `:2125`) run inside the
   resolve / write-back under the capture mutex and touch no hook state.
   `resource_reader::report()` is reached twice per process (telemetry
   summary via `loading_trace::report`, and `capture.cpp:458` when the last
   device is destroyed) but prints only when the call count moved
   (`resource_reader.cpp:143-149`), so no line is duplicated.
4. **No-SSE translation units.** `CMakeLists.txt:20-27` sets
   `-mno-sse;-mno-mmx;-mfpmath=387` on `engine_memory.cpp`,
   `loading_trace_light.cpp` and `resource_reader_core.cpp`;
   `build/CMakeFiles/d3d9.dir/flags.make` carries the three per-object
   overrides after the clean rebuild. `objdump -d` of the three objects:
   0 `%xmm`/`%mm`/`%st` operands and 0 x87 mnemonics each (`engine_memory`,
   `loading_trace_light`, `resource_reader_core`). `check_no_x87.py` roots are
   the union of the branches: 9 light setter hooks, 4 gz entry points, 35
   light loading rows and 5 `extern "C"` probe/reader/pool symbols = 53
   roots, 195 reachable functions, 0 violations on the clean build.
5. **`tools/manage.py`.** All flags of the three branches are present
   (`--loading-probes`, `--resource-read`, `--dat-handles`,
   `--mesh-adjacency-dump`, `--taa-debug` help updated for the present
   readback). `--dry-run` (validated JSON, `X3M_*` values that are not the
   default shown):

     `X3M_TELEMETRY=1 X3M_MESH_ADJACENCY=verify X3M_MESH_ADJACENCY_DUMP=1`.
   - run 4 (`--direct --ownership --object-trace --object-lifetime
     --motion-output --taa --taa-debug --telemetry --gz-buffer --taa-sharpen 0.5
     --taa-mip-bias -0.5 --capture-start 999999 --capture-frames 4`):
     `X3M_OWNERSHIP=1 X3M_OBJECT_TRACE=1 X3M_OBJECT_LIFETIME=1

     X3M_TAA_SHARPEN=0.5 X3M_TAA_MIP_BIAS=-0.5 X3M_SCENE_HOOK=1 X3M_TELEMETRY=1
     X3M_GZ_BUFFER=1 X3M_CAPTURE_START=999999 X3M_CAPTURE_FRAMES=4`.
   - **Finding 1 (low, fixed)** `tools/manage.py:47,84`: the `--loading-probes`
     help says "requires --telemetry" but no validation enforced it, and

     without telemetry (`loading_trace.cpp:866,957`), so
     `launch --direct --loading-probes` would have started a game with no
     probes and no diagnostic line. Added the `parser.error` next to the
