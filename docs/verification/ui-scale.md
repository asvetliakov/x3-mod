Feature: `--ui-scale S|auto` / `X3M_UI_SCALE` / `ui_scale`, `src/proxy/ui_scale.cpp`,
`src/proxy/ui_scale_sites.h`; eight engine sites claimed together or not at all
([architecture/ui-scale.md](../architecture/ui-scale.md);
[reverse-engineering/gui-scale.md](../reverse-engineering/gui-scale.md) section 5
strategy (b)). Default `1` = off; nothing is written unless the setting parses to
`auto` or a scale in (1, 3], the executable identity holds, every window matches,
and the device's back buffer (for `auto`) gives a scale above 1.

## Open

- Not yet flown. First flight: `--ui-scale 1.25` (or `auto`) with `--debug`
  at 5120x1440. Expect one `ui_scale … status=pending mode=fixed|auto` row at
  load, one `ui_scale_install … status=patched reason=ok virtual=4096x1152` row
  at device creation (writes per site: plain or atomic), a `ui_scale_camera`
  row whenever the excluded HUD camera changes (the first one `previous=0`
  once a cockpit exists), and one `ui_scale_frame … frames=300` row per 300
  Presents. The row settles open item 1 of the note: in
  flight the `excluded_camera=` pointer must appear in `cameras=` with
  `0x200` instances (the HUD scene is excluded, crosshair/target icons at real
  pixels), the menus' camera(s) must show the scaled count in `scaled=`, and
  the main menu should show no `0x200` instances (perspective path) or, if it
  does, its scaling is a decision to take. What the code cannot prove: that
  `cockpit+8` is the camera the renderer passes for the HUD scene's instances
  (the exclusion is by that pointer), that no script pixel size reaches a
  native call in real pixels, that the ticker and gravidar are `0x200`
  instances of a script scene, and the feel of the mouse under the remainder
  accumulator. The fixture-only `X3M_SUBMIT_PHASES=1` group and this feature
  refuse each other at the entry/caller bytes (documented).
