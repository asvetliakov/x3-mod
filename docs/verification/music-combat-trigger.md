# Combat-music trigger: verification ledger

Feature: `music_combat_trigger` / `--music-combat-trigger` (`X3M_MUSIC_COMBAT_TRIGGER=engaged|vanilla`, default
`engaged`) and `music_combat_hold_s` / `--music-combat-hold-s` (`X3M_MUSIC_COMBAT_HOLD_S`, 1..600 game seconds,
default 20), `src/proxy/music_alert.cpp` ([architecture note](../architecture/music-combat-trigger.md); engine facts
in [music-script-driver.md](../reverse-engineering/music-script-driver.md) sections 2, 5 and 9). One six-byte claim at
`0x0042c974` inside the alert routine `0x0042c890`; the handler lowers this frame's alert level `[R+8]` to 0 unless the
player is engaged within the hold (reasons a..f); `vanilla` patches nothing. Fails closed on the executable identity,
19 byte windows, the site bytes and the alert routine's call site.

## Open

- The list-array fix is unflown. The next flight's expectations are in the architecture note ("What the first flight
  must show"): the install row `armed=1 reason=ok write=plain windows=20` with and without `--debug` (game phases),
  `suppressed=start/end` for a hostile in range without a fight, `edge … reason=a … walk=ok fire=ok` on the first shot
  at a hostile, `visited` > 0 on every row with `vanilla` ≥ 1, `cause=expired` about 20 game seconds after the last
  stamp, `hostile_orders` and `cuts` sizes; any other `walk=` / `fire=` names the failing check.
- Not measured: the walk's cost per frame (object counts per sector are unknown; the vanilla routine visits a superset
  every frame) and whether the AI always fights through orders `0x10`/`0x11`.
- The re-baseline after a load that keeps the same player ship pointer and a later clock relies on the once-per-process
  `save_load_complete` marker; a second such load in one session could count the restored counter delta as one shot
  (one stamp, 20 game seconds of combat music at most, and only with a hostile in range).
