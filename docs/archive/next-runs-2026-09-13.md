## 7. Modern chase camera

The existing prototype `7f4b251` is integrated, reviewed/fixed and fixture-qualified. Camera mode
is **vanilla by default**; the earlier loading/graphics commands keep it off.
The first flight confirmed activation but reported subtle framing and trembling.
The native position-selection correction and lower framing are qualified and
installed. The elevated/closer update is also installed; use the common locked launch
prefix with:

```sh
--direct --camera chase --telemetry
```

In one session, first use first-person view and right-mouse fire in empty space
with the cursor left, centre and right. Hold each position for about 15 seconds
so the first-eight-event sampling window can refresh at its 300-frame report
boundary. Switch to the chase back view and
repeat. If practical, repeat with a selected target and note that separately.
This compares native input gates, cursor coordinates, camera pose and actual
weapon directions without changing firing behavior. No F8 capture is required
for this diagnostic.

Then fly straight, steer gently, and stop steering to let the camera settle.
Report whether trembling remains absent, whether the top of the hull is visible,
whether the whole ship fits, and whether the closer/softer view feels right.
Telemetry includes the
native position branch, position-domain separation, separate rotation/boom
clamp counts and lag ranges, plus handler CPU timing.

For the remaining camera acceptance, cycle F2 to the external back view, turn then stop, test target
brackets/aim, switch views, open/close the sidebar while lagging, toggle SETA,
and change resolution if practical. Report camera lag, ship placement and
distance. The installed defaults are rotation 0.22 s, boom 0.30 s, rotation clamp 8°, boom clamp
0.10, vertical offset 0.45 (nominally 72.5% screen height), downward pitch 20°
and distance scale 0.6. Combat tightness and scene fix
remain off.

For the patch-absence and frame-cost comparison, use the same installed build,
save and settings with `--direct --camera vanilla --telemetry`; expect no
`chase_camera` lines. Compare settled frame-time windows with the chase run.
Handler timings alone do not establish the total overhead.

A separate TAA-enabled run uses:

```sh
--direct --camera chase --ownership --object-trace --object-lifetime --motion-output --taa --telemetry --taa-debug --camera-log 1 --capture-start 999999 --capture-frames 4
```

Capture rest, turn and movement with F8; cross a gate if available.
`--camera-log 1` records every TAA camera decision so a one-frame cut cannot
fall between the default 300-frame samples. This diagnostic run is separate
from the plain vanilla/chase frame-cost comparison. We will check
all [thirteen architecture acceptance items](review-31-chase-camera-architecture.md#acceptance-criteria-for-the-first-user-run):

1. Active byte-verified installation; vanilla mode patches nothing.
2. Back view: `verdict=0`, `applied` grows, `refused` stays flat, `write_refused=0`. `refused_inactive` may grow for other cockpits; `cockpits_seen` stays stable.
3. Lag at most 8°, below 0.1° around one second after stopping; `dt_ms` approximates frame time and stays unchanged by SETA; `basis_dev_deg` is about zero in free flight.
4. Brackets and mouse aim remain aligned during lag.
5. Gate transition: `snap_reason` 16 then 4, `snaps` +2 and `coalesced` +1, exactly one `camera_cut=1`; no subsequent ghosting.
6. Internal/front/side/scripted/docking views retain vanilla poses with verdicts 1/2/3/7 as applicable; snap on undock.
7. Menu/sidebar behavior settles without a jump (A8, unverified).
8. TAA stable at rest; centred native anchor projects about 45% of half-screen height below centre (72.5% screen height); check the actual ship silhouette and lag in game.
9. Chase remains active after resolution/device recreation; `chase_camera_last_device kept=1` if the device was recreated.
10. Handler CPU timing from `chase_camera_timing` (telemetry enabled), plus frame-time comparison. The handler metric excludes the assembly stub/CPU save and restore; gameplay cost remains unverified.
11. Record first-applied tangent, `fov298`, plane/boom fields, resolution and aspect, with matching ref/view object and a valid back boom. The prior 1280×768 screenshot accompanied `half_vfov_tan=0.7500` and `fov298=0x4000`; the aspect mapping remains to be established, so do not require the older inferred 16:9 value.
12. Test none/target/enemy: check `tracking=0/1/4` and `locked=0/1` before enabling combat tightness.
13. View-boundary hysteresis prevents repeated snap/refusal oscillation; report verdict flips during front-to-back turns.

Exact counter semantics matter: the delayed sector update may record a second
spring re-seat with `coalesced` increasing, while emitting only one TAA cut.
Keep the optional scene fix off unless a one-frame-late HUD element is observed.
Velocity transport is a later option if rotation clamps above 30° are wanted.

## Analysis protocol

Copy the selected session log and its readbacks/dumps from the installed
capture directory into a new `/tmp/x3-bottleX3-run<N>/` directory before
analysis. Inspect filenames, timestamps and file sizes first; do not overwrite
an earlier snapshot. Copy only files belonging to that run, and distinguish
complete sessions from a still-running session. The capture directory is
reported by `tools/manage.py status` and the session's `capture_dir=` field.

Use bounded streaming analysis under `tools/analysis/` rather than reading a
large log whole. Record build provenance, flags, scene/save differences,
acceptance counters and phase timings in the verification document and update
`docs/status.md`. Keep raw logs, mesh dumps, textures and readbacks local and
untracked. Compare run 5 with the preserved `/tmp/x3-bottleX3-run16/` fixed-EV
baseline; if the scene differs, distinguish that from an exposure regression.
Run 16 had `taa_debug=0`, sharpen 0 and mip bias 0. Its snapshot initially
contained only the 59 MB log; a bounded scan identified seven successful
`hdr_` readbacks, recovered from the live capture directory by matching names,
sizes and modification times within the session. Their recovery hashes and
source metadata are saved locally in `recovered-hdr-inputs.json`. There are
no `taa_` or `present_` records, so those unresolved HDR inputs are not a
measured resolved/presented-image baseline.

For a scoped modeled comparison, use the **new** capture's
`taa_<device>_<frame>.rgba16f` and the validated AgX reference with exposure
multiplier 1.0 and matching decode/look/clamp settings. Pair it with a successful
same-device/frame `present_` readback without fallback/unwind. This models fixed
EV 0 write-back of the same resolved frame, before later game glow/HUD rendering;
it does not reconstruct a different temporal history or the old run's screen
image. `hdr_` is the unresolved scene input and is not the paired write-back
input. No extra launch is needed solely for this modeled comparison.

Separate diagnostic overhead and fixture microbenchmarks from game frame time
and uninstrumented load time. Verify-mode work is intentionally duplicated, so
its total load time does not predict fast-mode performance.
