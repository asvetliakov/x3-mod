# Exact Preview dynamic SYSTEMMEM readonly mapping

The independent installed-binary review supports extending the existing adjacency cache contract to mesh options `0x990`, `0x991`, `0x18990`, and `0x18991`. These select SYSTEMMEM and DYNAMIC for both buffers, with optional 32-bit indices and software processing. This conclusion permits targeted native/wrapped fixtures; it does not claim a measured game hit rate or a general D3D9 dynamic-buffer guarantee.

The retained evidence is `verification/results/mesh-dynamic-contract-review.json`. It records reviewed exact PE32 address ranges and freshly checked module digests. Raw instruction text remains local-only. D3D9 SHA256 is `58cc36cf74128ae4b6211100430d146c3692808146d8d2075e6c5d846162f8cf`; WineD3D SHA256 is `f4997bc0465de7e87bac9921bf0274db00ac3b3ba0754fa03f1f33e309a8e863`. All addresses here are RVAs relative to preferred base `0x10000000`. Native D3DX method identity and options preservation are separately documented in the live-cache fixture and iteration05 gate analysis.

| Boundary | Exact branch and implication |
|---|---|
| D3D9 buffer creation | VB `0x1300–0x13da`, IB `0x15c0–0x16ac`: SYSTEMMEM pool 2 yields access `0x0e` (CPU, MAP_READ, MAP_WRITE), without GPU access. DYNAMIC is consulted on the DEFAULT-pool branch, not SYSTEMMEM. The VB constructor can create a separate GPU draw resource, but the verified Lock method maps the original resource at object `+0x10`. |
| D3D9 lock conversion | `0x4160`: mesh Lock adds NOSYSLOCK, so cache READONLY becomes `0x810`. Conversion considers WRITEONLY usage, which the gate excludes, and produces `0x80000800`: MAP_READ plus NOSYSLOCK. There is no MAP_WRITE, DISCARD, or NOOVERWRITE. DYNAMIC and SOFTWAREPROCESSING do not alter this conversion. |
| WineD3D buffer creation | GL buffer initialization `0x1b800`, GPU-access test `0x1b86e`: no GPU access skips USE_BO creation. The DYNAMIC test is inside the GPU branch. Common initialization `0x1b4a2–0x1b51d` prepares heap storage for a no-BO buffer; allocation failure fails creation. Software vertex processing can pin heap storage, rather than introducing a GPU mapping. |
| Context map | `0x4c190`: MAP_READ follows the read branch and preserves the flags when DISCARD/NOOVERWRITE are absent. Its dynamic-usage checks belong to other flag branches. |
| Command-stream map | `0x37940`: the upload/rename shortcut requires `flags & 0x3000`, absent here. The ordinary path waits for prior resource work, requests a 28-byte map command, submits it and waits for completion. This is not a nonblocking or bounded-latency guarantee. |
| Resource map | `0x1c4f0`: without USE_BO, the mapping selects system memory. READONLY skips write-range invalidation at `0x1c61e`; the returned address derives from heap storage. GPU allocation/renaming branches are unreachable for this resource. Lazy materialization of initially cleared storage is possible; this does not overwrite populated application bytes. |
| Resource unmap | `0x1ca60`: subresource zero decrements map count. The heap route has no GPU map pointer, so it needs no GPU unmap. DYNAMIC does not introduce a new cleanup branch. |

The existing [matched-unlock contract](mesh-unlock-contract.md) therefore extends to these four options under the same assumptions: live, valid objects; serialized application access; paired successful readonly acquisition; ordinary immediate command-stream use outside backend callbacks; and unchanged verified forwarding boundaries. Its 16-byte unmap command uses the same preallocated immediate-queue route. Public D3D9 Unlock still discards the internal unmap HRESULT, so that public result alone remains insufficient proof. Unexpected cleanup failure remains a restart-required operational fault, not transparent fallback.

Activation must preserve the exact module hashes and live endpoint/import checks, recognized wrapper forwarding checks, buffer sizes/formats and SYSTEMMEM descriptors, and rejection of WRITEONLY, shared, other-pool, unknown-tracker and pending-lock cases. Cache code must keep calling through the recognized wrapper. The core capability remains false by default; the live adapter may grant it only after this runtime's full preflight and the explicit four-option whitelist. Different dynamic combinations and unrelated implementations are outside this activation decision.

The fresh six-case targeted matrix establishes native/miss/hit output, HRESULT, FP/LastError, bytes, refcounts, revisions and pending-lock behavior for all four variants, including mutation after a hit and downstream native CleanMesh/Optimize. Independent review verified the fixture assertions and all recorded source, executable, native-module and case-output hashes in `verification/results/mesh-cache-hook-summary.json`: 12,781 checks pass, with 20 hits and 16 misses in each enabled case. These are synthetic runtime results, not game performance evidence. Private tracker observations should describe operations actually performed, as in the existing cache contract. No ambiguity should be manufactured or cleared to make skipped native operations appear to have happened.

The upstream [D3D9 buffer implementation](https://github.com/wine-mirror/wine/blob/master/dlls/d3d9/buffer.c), [WineD3D buffer implementation](https://github.com/wine-mirror/wine/blob/master/dlls/wined3d/buffer.c), and [WineD3D command stream](https://github.com/wine-mirror/wine/blob/master/dlls/wined3d/cs.c) corroborate function roles. They are not asserted to be matching CrossOver sources; the pinned binary branches are the version-specific evidence.

The new diagnostics were independently reviewed at source level: fixed reason arrays bound storage; one CAS winner writes each immutable first-detail payload, then release-publishes state 2; reports acquire state 2 before reading. Counter publication can precede detail publication, but reports check detail readiness independently of count changes. The same pattern protects the first unsupported FP snapshot. No report acquires the mesh registry lock. Counter snapshots are cumulative observations rather than an atomic transaction across every metric; this is suitable for eligibility diagnosis. Runtime evidence for the updated code belongs to the author's fresh fixture reports.

Cross-contract reconciliation: the generic null-command return at emit-unmap `0x37bf6–0x37c27` is real and D3D9 discards its HRESULT. It is not an additional reachable allocation failure under this contract. Resource unmap `0x7b731–0x7b73c` selects the same device immediate context without examining resource pool. MT application-thread require-space `0x3c339–0x3c353` selects the preallocated ring; its null branch requires packet size plus seven to reach 4 MiB, impossible for this 16-byte packet. ST initialization allocates 4096 bytes at `0x38281–0x382a1`; ordinary top-level submit restores start/end to zero at `0x396ed/0x396f3`, so the next 16-byte packet cannot require growth. A managed WRITE mapping does not by itself change these allocator branches. Its later resource-handler and upload semantics require their own review; this readonly contract does not prove them. Backend reentry, corruption, patched dispatch and abnormal lifecycle remain excluded.
