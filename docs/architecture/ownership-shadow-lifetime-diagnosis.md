# Ownership shader shadow lifetime diagnosis

Status: **diagnosis confirmed; scoped-getter proposal ratified by the orchestrator on 2026-09-21** (scoped owned restoration references from the public shader getters, acquired before the first injected mutation, held through undo, released under the existing draw/device pin; no permanent shadow pins, no device_references change). Implementation is in progress in the `investigate/lattice-capture-lifecycle` worktree; the routed fixture case remains the first acceptance witness. Original text follows. Read-only investigation; no production changes, builds, Wine or game execution. Session-limit handoff, 2026-09-21.

## Confirmed outcome

The routed final-application-release fixture exposes a real latent ownership/MotionOutput lifetime defect. Retaining the fixture's shader creation references would mask it and would no longer establish the requested last-application-reference case. The fixture binds valid shaders and releases its own creation references; the original native shader backing remains bound. The proxy's separately reference-counted application wrapper is what expires.

Evidence: `/tmp/x3-lattice-capture-lifecycle/verification/probe/lattice_capture_lifecycle_fixture.cpp:142` (`drop_resources`) and `:148` (`guarded_release`); `/tmp/x3-lattice-capture-run-v1/stdout.log`; implementer `/root/lattice_subset_qualifier` independently mapped the fault to ownership Device::SetPixelShader → MotionOutput::undo → after_draw → guarded Capture submission. Earlier direct/child/explicit/deferred/Reset and unrouted guarded cases passed in that run; routed case crashes. This is not evidence that upload observation itself corrupts a shader.

## Source chain

* `src/proxy/motion_output.h:1112` Shadow stores raw VS/PS pointers. `motion_output.cpp:3437` and `:3462` assign them without retaining references. Capture updates them only after successful application setters; state-block recording suppresses ordinary shadow changes.
* `src/ownership/d3d9_ownership.cpp:767` release destroys a child wrapper at logical refs zero, erases both application/native identity maps, releases its native backing reference, then releases the child's single parent-device reference. Native device binding can keep backing alive independently. Each wrapper owns one parent reference; each extra shader AddRef does **not** own another device reference.
* `motion_output.cpp:3901` undo restores `shadow_.ps` and `shadow_.vs` after replacing native bindings with injected variants. The saved original wrapper may already be dead. `d3d9_forwarders_inc.h:556` unwraps SetPixelShader input; `d3d9_ownership.cpp:825` returns an unrecognized pointer unchanged for legitimate foreign native inputs. The dead wrapper therefore reaches the native implementation.
* `motion_output.cpp:3608` resync obtains live shader getter references, stores their pointers and immediately releases them. Thus existing resync does not establish a persistent lifetime contract. It also resets Shadow wholesale.
* `motion_output.cpp:352` device_references counts renderer-owned child objects, while `:377` release_resources breaks existing renderer/device cycles. `capture.cpp:825` final-release accounting uses those counts. Shader registration owns variants but not original shader pointers; no original-shader destruction notification was found.

## Recommendation and exact next action

Do not apply the initially attractive two-strong-shadow-reference patch without resolving its shared-child retirement contract. Continue one bounded implementation-design task: use **temporary owned restoration references acquired from public GetVertexShader/GetPixelShader before the first injected mutation**, retain them through undo, and release them only after restoration while the existing active-draw/device pin still protects Capture. The diagnostic fixture's unchanged routed last-app-release case is the first acceptance witness. This is a proposed narrow safety correction, not yet a ratified implementation.

The next author must first enumerate the existing paths that restore `shadow_.vs`/`shadow_.ps`, and establish one common scoped restoration contract for the paths actually injecting shader state. A getter failure or inconsistent state must decline injection before native state changes; original application submission still occurs exactly once. Own null bindings explicitly. Never restore a borrowed dead pointer as fallback. Do not add permanent application shader references merely to satisfy the fixture. Snapshot actual current state before replacement, not after a motion variant has been bound. Public COM getter references must remain owned through all success/failure/early-return restore paths. Existing final-release/draw pin ordering must cover their last Releases, including callback reentry.

This scoped approach deliberately pays getter/refcount cost on injected draws to establish correctness without a new persistent device cycle. No per-draw allocation is required beyond any ownership wrapper resurrection already needed by a public getter. Whether this cost is acceptable, and whether an existing scoped state snapshot can be reused, is **unresolved**; inspect that narrowly before coding. A counted fixture must report new GetShader calls and wrapper creation/refcount operations per routed draw, zero on unmodified draws, and no extra repeated acquisitions within one route. If unacceptable, ratify the larger persistent-reference/ownership-notification design explicitly rather than silently weakening lifetime guarantees.

## Why permanent shadow references need more than +2 accounting

Owning the two currently logical-bound shaders would avoid per-draw getters and is attractive for performance. Successful changed setters would AddRef new before releasing old; same-pointer setters would refresh metadata without ref churn; resync must acquire getter references before dropping old pins; teardown must clear pointers/metadata before callback-capable Releases. All are necessary but insufficient.

An original shader can be jointly held by the application and renderer through one child wrapper with only one parent-device reference. Blindly adding one device_references count per owned shadow shader labels that shared parent reference renderer-only and can release renderer resources early when the application still holds the shader and can reacquire the device with GetDevice. Conversely, excluding the shared child initially leaves a cycle when its later application shader Release changes wrapper refs from two to one: no parent Device::Release occurs at that transition, so the existing final-device-release hook is not notified. Therefore strong shadow references require a proven ownership-aware transition notification/accounting contract (or another complete cycle-breaking mechanism), including native/unwrapped behavior. That mechanism is not established in this diagnosis. Do not claim simply counting two pins solves it.

Owning every registered original shader has the same problem with larger retention. Invalidating shadow on wrapper destruction alone cannot restore a native original after injection and would drop enhancement for legal bound shaders. Modifying unwrap to reject all unrecognized pointers breaks valid foreign-native inputs and does not recover the correct original. Per-route public getters avoid persistent cycles but do not independently solve old weak registry-key reuse or state-block wrapper resurrection/profile-registration gaps; those are separate unresolved identity issues and must not be described as fixed.

## Native Windows and acceptance

Use documented D3D9 shader getters/setters and IUnknown AddRef/Release only; no private Wine layout/hash requirement. This is a Windows-compatible proposed contract, **not native Windows execution evidence**. Existing owned State snapshots already demonstrate scoped COM handling patterns in `motion_output.cpp` near its opening helper structures. Native public getter behavior and ownership-on behavior both require focused fixture coverage.

Required bounded checks after parent ratification: (1) unchanged ownership-on routed final-app-release fixture completes with original submission once and correct CPU/LastError, restored original VS/PS, balanced references and actual device retirement; (2) VS-only, PS-only, null bindings, failed getter and failed injected setter paths restore/decline correctly; (3) same-pointer rebinding and state-block Apply/resync do not resurrect stale restoration pointers; (4) application shader refs retained across Device::Release/GetDevice remain legal and do not cause premature teardown, then eventual shader/device release retires; (5) Reset success/failure and resource teardown do not leak scoped restoration refs; (6) measure added calls per injected versus ordinary draw. Parent owns any Wine execution and frozen-candidate rerun; preserve the current failing artifacts.

Owning documentation follow-up, after ratification: `docs/architecture/live-motion-route.md` describes no retained application COM refs across frames and logical device-reference accounting; amend only if final design changes that contract. State-call fast-path documentation must report any new routed-draw getter cost. No claim that lattice crawl or upload payload qualification is fixed by this lifetime repair.
