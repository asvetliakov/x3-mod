# FL camera provider

`src/engine/fl/camera_state_fl.cpp` implements `src/proxy/camera_state.h` for the `fl` edition (the ap
target keeps `src/proxy/camera_state.cpp`; [farnhams-legacy-build.md](farnhams-legacy-build.md)).
Read-only engine memory, no hook, no patch; `MotionOutput::read_camera` is the consumer. Same latch as
AP (`X3M_MOTION_OUTPUT=1` with `X3M_TAA=1`, the shadow-replay switches, `request_consumer`, or
`X3M_CULL_SMALL_PARTS_PX`), same failure codes and per-pointer `VirtualQuery` cache. FL consumers (the
light-map far fade, the TAA far gate and sentinel policy) take the matrices as soon as the anchors
match: there is no separate acceptance step.

## Slots, anchors, layout

Candidate from [camera-buffers.md](../reverse-engineering/fl/camera-buffers.md): the renderer
allocates two 64-byte buffers at initialization and publishes them in `.data` pointer slots, view RVA
`0x1aae68`, perspective RVA `0x1aae78` (the orthographic slot `0x1aae4c` is not read). X3FL.exe is
relocatable (FL run 1 base 0x4d0000): every address is `fl::module_base() + RVA`. `initialize()` admits
the slots only after both publication sites verify as whole instructions at `base + 0xda01a` /
`base + 0xda036`: `mov ecx,0x40; call <allocator 0xd8fc0>; mov [slot],eax; test eax,eax` (17 bytes), the
store's disp32 (the only relocated word) equal to `base + slot RVA`. Constants: generated by
`tools/analysis/fl_camera_constants.py` into `camera_state_fl_inc.h` (`--check`); host test
`verification/analysis/test_fl_camera_state.py`. Status: `disabled`, `executable_mismatch`,
`anchor_mismatch`, `slots_unreadable`, `active`. Layout: row-major, row-vector D3D (v' = v * M), what
`camera_reprojection.h` consumes (setter 0x4ded90: P[11] = 1, view = transposed fixed-point basis,
translation in V[12..14]; note section 2). No transpose. P[10]/P[14] are per-submission depth scratch.

## Diagnostic rows (`x3m::log`, always tier)

Once, at `initialize()` or on a status change: `fl.camera status= base=0x… view_slot=0x… proj_slot=0x…
view_buffer=0x… proj_buffer=0x… log_s=` (buffers still 0 at DLL load). Then from `read()`, every
`X3M_FL_CAMERA_LOG` seconds (`fl_camera_log`, default 10, 0 off; one QPC per read outside a burst, no
allocation) the next two consecutive reads are logged: `fl.camera_sample k=0|1 status= read_failure=
failure= reads= proj=0x… view=0x… shape=persp|ortho|other finite= m00= m11= m22= m23= m32= aspect=
ortho_dot= ortho_len= t_len= changed=0|1`. Under the current `motion_output` order k=0 is the
background/sky read (latching Clear) and k=1 the scene read (depth-only Clear); both rows together are
the proof, one alone is nearly always the background camera. `changed` compares with the previous row
of the same k and ignores P[10]/P[14], so changed=1 means the camera moved. Correct slots:
`read_failure=0 shape=persp m23=1`, `aspect` = m11/m00 = width/height (5120x1440: 3.556), `m11` =
1/tan(FOV_y/2) (about 1.0-1.7), `ortho_dot`/`ortho_len` below 1e-3 (AP ~1e-5), k=1 `t_len` the eye's
distance from the sector origin in the scene view (k=0 may differ), `changed=1` while flying. Wrong
slot: the orthographic slot gives `shape=ortho` (P[11] = 0, P[15] = 1); a world/scratch matrix
`read_failure=4` with `failure=` naming the first failed check; a null or freed buffer `read_failure=2/3`;
constant `changed=0` over a flight means a stale buffer. Known risk (camera-buffers.md section 4): the
orthographic UI pass overwrites the global view with identity; an identity view passes validation, and
the row then shows `t_len=0` with `ortho_dot=0` exactly on k=1.
